Subscribe to Publication

Anonymous newsletter sign-up with a double opt-in. No sign-in required.

<next-subscribe-to-publication>
Submitting writes nothing. Opening the emailed link does. Step 1 validates, seals the submission and sends one email — it does not even read a Contacts row, which is what makes the response identical for an address MP knows and one it has never seen. Following the link creates a dp_Contact_Publications row and, for an unknown address, a Contacts + Households pair in a real CRM — so use a test address. The link is single-use: opening it twice shows the “all set” state rather than confirming again, because a replayable link would silently re-subscribe anyone who had since unsubscribed.

These three are remembered in localStorage and re-applied on load, so they survive the email round trip — the confirmation link lands back on this page in a fresh browser navigation, and without that the widget would come back on its defaults. Try 1 for the publication id to see the publication_not_found state: on the reference instance that row is not Available_Online, and it is answered exactly like an id that does not exist so the id space cannot be probed for internal lists.

Widget CodePut this wherever “sign up for our newsletter” belongs

<!-- The minimum. Both attributes are required:
     publication-id is a dp_Publications row that must be
     Available_Online, and verification-email-template-id is a
     dp_Communications id whose Body renders [mpp_verify_email_url]. -->
<next-subscribe-to-publication
  publication-id="4"
  verification-email-template-id="5125">
</next-subscribe-to-publication>

<!-- The page's origin MUST be in EMBED_ALLOWED_ORIGINS, or no token is
     minted and every visitor sees an error. This is setup failure #1. -->

<!-- Everything else is optional. -->
<next-subscribe-to-publication
  publication-id="4"
  verification-email-template-id="5125"
  return-url="https://www.example.church/newsletter"
  my-subscriptions-url="https://www.example.church/email-preferences">
</next-subscribe-to-publication>

<!-- return-url is where the emailed link lands, and it must be
     same-origin with the page (https, no embedded credentials) or the
     request is refused and no email is sent. It defaults to the current
     page URL with the query string stripped, so most sites need it only
     when the form and the landing page differ. -->

<!-- Four merge tokens are available in the verification template:
       [mpp_verify_email_url]      the confirmation link — required
       [mpp_contact_first_name]
       [mpp_contact_last_name]
       [mpp_publication_title]     new; legacy could not name the list -->

<!-- Migrating from mpp-subscribe-to-publication? Four things changed.
     1. The query parameter is nextwidgets_verify, not mpp-verify-id.
        Override it with verify-param-name if a template already in the
        wild hard-codes the old one.
     2. The mobile-phone field and the signed-in "Subscribe As" household
        dropdown are not ported. A member managing household
        subscriptions has next-subscriptions.
     3. The link is single-use and lives 3 days (legacy: replayable, 24
        hours). A second click says "you're all set", not "thanks again".
     4. A contact's Email_Address is never overwritten. Legacy set it to
        whatever the public form held, which let anyone take over an
        account by naming its contact id. -->

<!-- Listen to events -->
<script>
  const widget = document.querySelector("next-subscribe-to-publication");
  widget.addEventListener("verificationSent", (e) => {
    console.log("Confirmation email sent to:", e.detail.email);
  });
  widget.addEventListener("subscribed", (e) => {
    // { publicationId, email, alreadySubscribed }
    console.log("Subscription confirmed:", e.detail);
  });
  widget.addEventListener("subscribeFailed", (e) => {
    console.error("Error code:", e.detail.code);
  });
</script>
