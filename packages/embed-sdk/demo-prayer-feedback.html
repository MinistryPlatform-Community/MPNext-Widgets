Prayer & Feedback

Prayer requests, praise reports and general feedback, written to MP's Feedback Entries. No sign-in required.

<next-prayer-feedback>
A signed-out submission writes nothing until the emailed link is opened. That double opt-in is the whole design: without it an unauthenticated POST could mint Households and Contacts rows in a real CRM as fast as a script can manage. Once you follow the link, this widget does create a Feedback_Entries row (and, for an address MP has never seen, a household and contact) — so use a test address. A signed-in submission skips the round-trip and writes immediately; sign in through the user menu demo first to see that path and the “Provide Feedback As” household picker.

Leave Feedback type IDs blank to see the safe default: every Feedback_Types row except the user-removal type, which legacy offered by default and which is a data-erasure workflow rather than a prayer request. Type 1,2,5 to get it back — an explicit list is honoured, with a warning in the console. Clearing the verification template shows the “not configured” state a misconfigured page gets at load, instead of after a visitor has typed 2000 characters.

Widget CodePut this on your prayer / contact page

<!-- The minimum. `verification-email-template-id` is a dp_Communications
     id whose Body must render [mpp_verify_email_url]; without it a
     signed-out visitor has no way to confirm, so the widget renders a
     configuration notice instead of a submit button. -->
<next-prayer-feedback
  verification-email-template-id="5125">
</next-prayer-feedback>

<!-- The page's origin MUST be in EMBED_ALLOWED_ORIGINS, or no token is
     minted and every visitor sees an error. This is setup failure #1. -->

<!-- Everything else is optional. -->
<next-prayer-feedback
  feedback-type-ids="1,2,3"
  program-id="12"
  verification-email-template-id="5125"
  acknowledgement-email-template-id="5126"
  return-url="https://www.example.church/prayer"
  default-private="true">
</next-prayer-feedback>

<!-- A page framed entirely as confidential pastoral care: hide the
     checkbox and force every request to Staff Only visibility. -->
<next-prayer-feedback
  verification-email-template-id="5125"
  default-private="true"
  hide-private-option="true">
</next-prayer-feedback>

<!-- Migrating from mpp-prayer-feedback-form? Three things changed.
     1. Omitting the type list no longer offers "User Removal Request";
        list it explicitly if a church really wants it on a public form.
     2. Signed-in submitters get no verification email, only the
        acknowledgement. Fewer emails is intended, not a broken template.
     3. A prayer-wall page must filter on
        Approved = 1 AND Visibility_Level_ID = 4 — never visibility alone.
        Approved is always false at intake, with no attribute to change it. -->

<!-- Listen to events -->
<script>
  const widget = document.querySelector("next-prayer-feedback");
  widget.addEventListener("feedbackSubmitted", (e) => {
    console.log("Filed:", e.detail); // { feedbackEntryId }
  });
  widget.addEventListener("verificationSent", (e) => {
    console.log("Confirmation email sent to:", e.detail.email);
  });
  widget.addEventListener("feedbackVerified", (e) => {
    console.log("Link redeemed:", e.detail); // { feedbackEntryId }
  });
  widget.addEventListener("feedbackError", (e) => {
    console.error("Error:", e.detail);
  });
</script>
