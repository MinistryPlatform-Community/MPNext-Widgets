# `next-add-to-calendar` — plan

**Items:** C06 (functional — non-public event data served to anonymous callers)
**Cutover verdict: fix before cutover. Small, self-contained, and it is a data-exposure item.**
**Owns:** `src/services/addToCalendarService.ts`, `src/app/api/embed/add-to-calendar/route.ts`

## What the feedback says

`AddToCalendarService.getEventForCalendar()` filters on the id and nothing else —
`filter: \`Event_ID = ${eventId}\`` (`:56`). No `Visibility_Level_ID`, no `Cancelled`. The
route in front of it is deliberately public, which is right for a public event, but the
combination hands out **any event by id**.

Measured from an anonymous page with `sub: "public"`, adjacent requests:

```
GET /api/embed/add-to-calendar?eventId=759   -> 200  (Visibility_Level_ID = 2, not public)
GET /api/embed/add-to-calendar?eventId=758   -> 200
GET /api/embed/event-details/759             -> 404  {"error":"Event not found"}
```

**The sibling route already enforces the rule correctly.** That inconsistency is the tell: the
intended predicate is written down in `eventDetailsService.ts` and this one route does not
apply it.

Rendering `<next-add-to-calendar event-id="759">` produces a fully working menu for the private
event, including Google/Outlook/Yahoo URLs and a downloadable `.ics` carrying its title and
description. Ids are sequential, so the table is enumerable one integer at a time, and the
endpoint carries `Cache-Control: public, max-age=300`, so a shared cache can hold the
responses.

## Why it matters more than the payload size suggests

Event title, full description, start/end and — where a Location is set — the **venue name and
street address**, for events the church has explicitly marked non-public. Internal staff
meetings, counselling groups, recovery-ministry meetings and leadership retreats all commonly
live at a non-public visibility level with a real room and address. On a customer site the
endpoint is reachable from any allowlisted origin with a public token the SDK mints
automatically, so no credentials are needed.

## Where the new widget is already better — protect this

**The widget itself is one of the run's strongest results.** From the README's "what passed"
list:

> `next-add-to-calendar` is correct in **every value checked** across Google, Outlook, M365,
> Yahoo and the `.ics`, using a fixture containing `&`, `,`, `;`, a newline and HTML —
> including 75-octet line folding.

It is also the SDK's **reference implementation for menu accessibility**: `role="menu"` with
`aria-label`, `aria-expanded` on the trigger, roving arrow-key focus, first option focused on
open, focus returned to the trigger on Escape. `CROSS-3` §4 lifts that pattern out of this
file for the calendar modal and the user menu.

And there is no legacy counterpart, so nothing here is a regression — this is a new capability
that got one predicate wrong.

**Do not reintroduce a calendar library.** `CLAUDE.md` is explicit: `add-to-calendar-button`
was removed on 2026-09-08 (ELv2-licensed, and the jsDelivr URL pinned CDN-generated bytes
rather than published ones). `shared/calendar-links.ts` replaces it in ~438KB less. The whole
surface is four query strings and a text file.

## Course of action

### The fix

```ts
filter: `Event_ID = ${eventId} AND Cancelled = 0 AND Visibility_Level_ID = 4`,
```

A non-public id then falls through the existing `if (!event) return null` and the route's 404 —
matching `/api/embed/event-details/:id` exactly.

### Two things to decide while in there

1. **Should a signed-in staff user be able to add a private event to their own calendar?**
   Plausibly yes. If so, thread `claims` through and relax the predicate only for that case.
   **The public default must be public-only** regardless. Do not make this the reason to delay
   the fix — ship the strict predicate now, add the authenticated relaxation later if anyone
   asks for it.
2. **Cancelled events.** The filter adds `Cancelled = 0`, which is right for "add this to your
   calendar". But an event that is cancelled *after* someone added it is a different problem
   the `.ics` cannot solve. Out of scope, worth noting.

### Then sweep

The item's last line is the durable part: **check the same predicate on every other
public-token route that reads `Events` by id.** This is a class, not an instance — one route
in the events family got the rule right and one did not, and nothing enforces which. A short
audit of `src/app/api/embed/*` for `Events` reads under a public token is worth an hour.

### Pin it

Add a case to `src/services/addToCalendarService.test.ts` asserting a `Visibility_Level_ID = 2`
id returns `null`. On this instance the level counts are 1 / 239 / 0 / **518** / 0 for levels
1–5, so there is no shortage of test ids.

## Do better than parity

- **A shared `publicEventFilter()` helper.** Both services now hand-write
  `Cancelled = 0 AND Visibility_Level_ID = 4`. One exported constant or helper in the events
  services makes the rule greppable and makes the next service inherit it rather than restate
  it. That is the change that actually prevents the third occurrence.
- **Reconsider `Cache-Control: public, max-age=300`.** Once the predicate is right the
  response only contains public data, so the header is defensible — but a shared cache holding
  per-event responses keyed only by id is worth a deliberate yes rather than an inherited
  default.

## Acceptance

- `GET /api/embed/add-to-calendar?eventId=<non-public id>` returns 404, matching
  `/api/embed/event-details/<same id>`.
- A cancelled event returns 404.
- A public event still produces correct Google / Outlook / M365 / Yahoo URLs and a valid
  `.ics` — the existing value-parity assertions must still pass.
- A unit test covers the non-public case.
- No other public-token route serves an `Events` row without the same predicate.

## Depends on / unblocks

Fully independent. One of the smallest fixes in the backlog and it should not wait behind
anything.
