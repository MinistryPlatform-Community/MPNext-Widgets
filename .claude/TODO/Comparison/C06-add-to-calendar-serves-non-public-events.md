# C06. `/api/embed/add-to-calendar` serves non-public and cancelled events to an anonymous token, while `/api/embed/event-details/:id` correctly 404s the same event

**Widget:** `next-add-to-calendar` (new only)
**Severity:** functional
**Confidence:** confirmed — both endpoints called with the same public widget token in the same page context
**Found:** 2026-09-08, comparison run

## Old behaviour

No legacy counterpart exists for this widget, so the reference is **our own sibling
route**, which enforces the rule correctly, and MP's visibility model:
`Visibility_Level_ID = 4` is the public level (518 events on MPI), `2` is not (239
events, titles like `Sunday Service - 2026-07-05`).

## New behaviour

`AddToCalendarService.getEventForCalendar()` filters on the id and nothing else —
`filter: \`Event_ID = ${eventId}\`` (`src/services/addToCalendarService.ts:56`). No
`Visibility_Level_ID`, no `Cancelled`. The route in front of it
(`src/app/api/embed/add-to-calendar/route.ts:18`) is deliberately public
(`requireWidgetAuth(req, { widget: ["add-to-calendar", "user-menu"] })` with no
`claims.sub !== "public"` gate), which is right for a public event but means the
combination hands out any event by id.

Measured from an anonymous page (`sub: "public"`), same token, adjacent requests:

```
GET /api/embed/add-to-calendar?eventId=759   -> 200
  {"Event_ID":759,"Event_Title":"Sunday Service - 2026-07-05",
   "Description":"Generated by MPNextTools synthetic data generator",
   "Event_Start_Date":"2026-07-05T10:00:00","Event_End_Date":"2026-07-05T12:00:00",
   "Time_Zone":"America/New_York", …}
GET /api/embed/add-to-calendar?eventId=758   -> 200   (same shape)
GET /api/embed/event-details/759             -> 404   {"error":"Event not found"}
```

Events 758 and 759 are `Visibility_Level_ID = 2` — not public. Rendering
`<next-add-to-calendar event-id="759">` on the demo page produces a fully working
menu for the private event, including a Google/Outlook/Yahoo URL and a downloadable
`.ics` carrying its title and description. Ids are sequential, so the whole table is
enumerable one integer at a time; the endpoint also carries
`Cache-Control: public, max-age=300`, so a shared cache can hold the responses.

## Why it matters

The payload is small but it is not nothing: event title, full description, start/end
and — where a Location is set — the venue name and street address, for events the
church has explicitly marked non-public. Internal staff meetings, counselling groups,
recovery-ministry meetings and leadership retreats all commonly live at a non-public
visibility level with a real room and address. On a customer site the endpoint is
reachable from any allowlisted origin with a public token that the SDK mints
automatically, so no credentials are needed. The inconsistency with
`/api/embed/event-details/:id` is the tell: the intended rule is already written down
in the neighbouring service and this one route does not apply it.

## Where to fix

`src/services/addToCalendarService.ts:52-59` — the `getEventForCalendar` filter. The
sibling that gets it right is `src/services/eventDetailsService.ts` (the query behind
`GET /api/embed/event-details/:id`); mirror its predicate.

## Suggested fix

Add the public-visibility and cancelled predicates to the `Events` read:

```ts
filter: `Event_ID = ${eventId} AND Cancelled = 0 AND Visibility_Level_ID = 4`,
```

so a non-public id falls through the existing `if (!event) return null` and the route's
404. If a signed-in staff user should be able to add a private event to their own
calendar, thread `claims` through and relax the predicate only for that case — but the
public default must be public-only. Worth adding a case to
`src/services/addToCalendarService.test.ts` asserting a `Visibility_Level_ID = 2` id
returns `null`, and checking the same predicate on any other public-token route that
reads `Events` by id.

## Resolution — 2026-10-11

**Fixed** (W2, branch `ws/w2-events`).

- New `src/services/_shared/public-events.ts`: `publicEventFilter(clause, prefix?)` and
  `publicEventPredicate(prefix?)` are the single definition of "an event a public widget may
  show": `Cancelled = 0 AND Visibility_Level_ID = 4`. The clause is parenthesised so an `OR`
  inside it cannot bypass the predicate. `Visibility_Levels` re-verified live via MCP:
  1 Private · 2 Staff Only · 3 Staff & Church · **4 Public** · 5 Hidden: URL Required (a
  system lookup with fixed ids, so it is not resolved through `getIdByValue`).
- `AddToCalendarService.getEventForCalendar` now reads through it, so a staff-only or
  cancelled id returns `null` and the route answers 404, the same answer as a missing id,
  so the id space cannot be probed.
- `FullCalendarService.getEvents` and `getEventDetail` use the same helper.
  **Sweep finding fixed:** `getEventDetail` (`GET /api/embed/full-calendar/:id`) filtered
  `Visibility_Level_ID = 4` but not `Cancelled = 0`, so a cancelled event's modal still
  opened by id.
- Both routes' 404 bodies are now the wire code `event_not_found` (previously English prose,
  `Event not found: <id>`), which the catalogue already translates.
- Tests: `public-events.test.ts`; `addToCalendarService.test.ts` asserts the predicate is
  sent and that a staff-only (759) or cancelled id resolves to `null` with no follow-up reads;
  `fullCalendarService.test.ts` pins the detail filter including `Cancelled = 0`.

**Sweep of every `Events` read reachable from `src/app/api/embed/*`:**

| Reader | Token | Verdict |
|---|---|---|
| `addToCalendarService.getEventForCalendar` | public | **was leaking; fixed** |
| `fullCalendarService.getEvents` | public | already public-only; now via the helper |
| `fullCalendarService.getEventDetail` | public | **missing `Cancelled = 0`; fixed** |
| `eventDetailsService.getEventById` (`api_MPPW_GetEventById`, `@IsStaffUser`) | public | the proc enforces visibility (759 → 404, measured in this item); no `$filter` to change. W1-owned. |
| `eventDetailsService.checkPendingEventAvailability` | public | reads only `Participants_Expected` and returns a boolean; no event data leaves. W1-owned, left alone. |
| `eventFinderService` (`api_MPPW_SearchEvents` → `api_MPPW_GetEvents`) | public | ids come from the search proc, which applies MP's own public rule; parity 34/34 with legacy. |
| `productsService.buildIsHiddenResolver` | public | reads `Event_Start_Date` only, to hide price options; nothing returned. |
| `preCheckService` (`api_MPPW_GetPreCheckEvents`) | **signed-in only** (route rejects `sub === "public"`) | n/a |
| `opportunityDetailsService` (`Add_to_Event_Table.Event_ID`) | n/a | reads an id only |

**Decided:** strict public-only now; no signed-in staff relaxation until someone asks for it
(epic decision table). `Cache-Control: public, max-age=300` on add-to-calendar is kept, since
the body now holds only public data. A `.ics` for an event cancelled after download remains
out of scope.
